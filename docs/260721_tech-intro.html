★ 이번 핵심 — 스키마 드리프트 전수 대조
🔴 원칙 13-9: 검수는 코드가 아니라 살아있는 DB에 대고 하라
코드가 select('컬럼')하는 모든 컬럼이 실제 DB에 존재한다는 보장은 없다(이름이 바뀌었거나, DDL이 실행 안 됐거나). 없으면 쿼리는 조용히 400으로 실패하는데, 에러 삼킴 패턴 때문에 화면은 빈 채로 "정상인 척" 동작한다. 코드 리뷰만으로는 절대 못 잡고, 살아있는 DB에 실제 쿼리(HTTP 200/400)를 날려야만 잡힌다. "수차례 전면검수에도 이상없다"던 버그들이 반복해 새어나간 근본 이유. 
# 에러 삼킴 안티패턴 — 400이 나도 data=null로 조용히 넘어감
const { data } = await db.from('businesses').select('region', ...);

# 검증 방법 — 컬럼 존재를 살아있는 DB에 직접 확인 (200=존재 / 400=부재)
curl -s -o /dev/null -w '%{http_code}' \
  "$SB/rest/v1/businesses?select=plan&limit=1" \
  -H "apikey: $ANON" -H "Authorization: Bearer $ANON"
결과: 클라이언트(45개 테이블) 9건 + 서버함수(admin.js/coupon.js) 7건 = 코드 16건 색출·수정. 한계: URL 쿼리 컬럼은 스크립트로 전수 대조되지만, INSERT/PATCH 바디 키와 obj.컬럼 속성 접근은 코드를 눈으로 읽어야 잡힘(coupon.js가 그 사례).

이번에 확립된 검수 원칙
⚠️ 13-9 — 검수는 코드가 아니라 살아있는 DB에 대고 하라
스키마 드리프트(코드는 특정 컬럼을 조회하나 실제 DB엔 그 컬럼이 없어 조용히 400)는 코드 리뷰로는 원리적으로 못 잡는다. 어떤 모델이든 코드만 읽으면 놓치고, 살아있는 DB에 curl로 200/400을 대조하면 잡는다. 이건 모델 역량이 아니라 검증 방법론의 문제. 배포 전 curl 대조를 CI로 자동화하는 것이 근본 재발 방지책.
⚠️ 13-8 — 재해석 대신 복붙 (07.17 확립)
이미 정답을 찾아 동작하는 화면이 있으면, 새 화면에서 원리를 재해석해 다시 짜지 말고 그 코드를 그대로 복사하라. 키보드가림을 채팅에서 이미 푼 방식(패널 자체 축소)으로 통일한 것이 계기. 배포 체크리스트 강제항목으로 편입.
