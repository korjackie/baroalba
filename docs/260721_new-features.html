Critical · Schema Drift
🔍 조용히 죽어있던 기능 16건 — 코드↔실제DB 전수 대조
"수차례 전면검수에도 이상없다"던 기능들이 실은 없는 컬럼을 조회해 조용히 400으로 죽어있었음. 살아있는 DB에 직접 대조해 일괄 색출.
ROOT CAUSE
에러 삼킴 패턴이 빈 화면을 "정상인 척" 만들고 있었음
const { data } = await db.from(...)처럼 error를 구조분해하지 않으면, 없는 컬럼을 조회해 서버가 400을 줘도 data=null로 조용히 넘어가 화면이 빈 채로 정상처럼 보임. 코드 리뷰로는 원리적으로 못 잡고, 살아있는 DB에 실제 쿼리를 날려야만 드러남 — 원칙 13-9로 확립.
CLIENT · 9건
클라이언트 화면 9건 (v547)
businesses.region(없는 컬럼)을 조회하던 4개 화면, 모임 지원자·레슨 문의·커뮤니티 댓글 알림 등에서 잘못된 컬럼/임베딩을 실제 스키마에 맞게 교정. 대부분 사용자에겐 "왜인지 목록이 안 뜨는" 증상으로 보였던 것들.
SERVER · 7건
관리자·쿠폰 서버함수 7건 (admin.js / coupon.js)
관리자 지원통계(created_at→applied_at), 회원 리뷰 표시, admin에서 모임 주최자 이름이 항상 공란이던 조인키 버그. 쿠폰은 지급 티켓수 undefined·사용 카운터 미증가에 더해, 1인당 재사용 제한이 전혀 안 걸려 같은 쿠폰을 무한 사용할 수 있던 문제까지 방어.
P0 Closed
💳 "결제해도 플랜이 free로 리셋"되던 문제 근본 종결
문서에 오래 남아있던 P0. 여러 번 손댔지만 재발하던 이 문제의 진짜 원인을 이번에 특정.
ROOT CAUSE + DDL
진짜 원인은 없는 businesses.plan 컬럼에 PATCH하던 것
결제 승인(toss-confirm.js)이 끝나면 businesses.plan에 플랜을 쓰는데, 그 컬럼이 실제 DB에 없어 400으로 실패하고 있었음. 구독 자체는 subscriptions 테이블에 정상 저장되지만 클라이언트는 businesses.plan을 읽으니 항상 free로 보였던 것. 컬럼을 추가하고 기존 결제자를 백필하자, 로그인 시 이미 select('*')로 plan을 읽고 있던 코드가 즉시 정상 동작 — 결제→재로그인 전 과정 종결.

Infra & Principles
📐 이번에 확립된 검수 원칙
PRINCIPLE 13-9
검수는 코드가 아니라 살아있는 DB에 대고 하라
스키마 드리프트는 코드 리뷰로 원리적으로 못 잡는다. 배포 전 curl로 컬럼 존재(HTTP 200/400)를 실제 DB에 대조하는 것을 원칙화. 모델(소넷/오푸스) 역량 문제가 아니라 검증 방법론의 문제라는 점을 명시.
