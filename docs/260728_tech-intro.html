★ 이번 핵심 2 — 8개 언어가 사실상 도달 불가능했다
🗣️ 저장된 언어 선택이 없으면 무조건 한국어 — 브라우저 언어 감지 코드가 아예 없었음
여러 세션에 걸쳐 8개 언어를 전부 번역해뒀지만, navigator.language를 읽는 코드가 저장소 어디에도 없어 그 언어 사용자에게 자동으로는 닿지 않고 있었음. 저장값이 없을 때만 브라우저 언어를 따르도록 수정(사용자 선택 항상 우선, 감지값 자체는 저장 안 함 — 저장하면 휴대폰 언어를 나중에 바꿔도 최초 1회 값에 묶임). 
// 네팔어 코드 불일치 — 표준(ISO 639-1)은 'ne', 앱 내부 키는 국가코드 'np'
// 매핑 없으면 네팔 휴대폰이 조용히 한국어로 떨어짐. 랜딩 JSON-LD inLanguage 도 동일 적용
browserLang === 'ne' ? 'np' : browserLang  // toApp 변환
결과: 홈 화면 렌더링 신규 키 약 45개(i18n 4차) + 하드코딩 토스트 155건(고유 127개) 등 총 158개 신규 키 × 8개국어(i18n 5차) 전수 번역. 랜딩 페이지도 본문 83개 키로 8개 언어 지원.
★ 이번 핵심 3 — 업주 알림 0건, 원인이 3겹이었다
🔔 스키마 드리프트 사본 누락 + 알바생 전용 종 + 뱃지 부재
_fetchOwnerNotifications가 라이브 DB에 없는 applications.updated_at을 select해 쿼리 전체가 400 → (data||[])가 조용히 빈 배열. 2026-07-19에 알바생 쪽은 이미 applied_at으로 고쳤는데 업주 쪽 사본을 놓쳤던 것 — 같은 로직이 파일 안에 두 벌 존재한다는 전제 없이 한 벌만 고쳤기 때문. 여기에 홈 화면 종이 알바생 알림만 보고 업주 알림은 별도 종에만 있었던 것, 그 홈 종에 뱃지 요소 자체가 없었던 것까지 3겹. 
// supabase/schema.sql:81 에는 updated_at 이 있다 — 스키마 파일과 실 DB가 다름
// 컬럼 존재 여부는 문서가 아니라 라이브 REST로 확인할 것
curl -s -o /dev/null -w '%{http_code}' \
  "$SB/rest/v1/applications?select=applied_at&limit=1" \
  -H "apikey: $ANON" -H "Authorization: Bearer $ANON"
결과: 전 쿼리 applied_at 통일 + #home-noti-badge 신설 + 홈 종이 업주 알림도 합쳐 최신순 정렬. 업주 전용 계정이 workers 행이 없어 조기 탈출하던 분기도 함께 방어.
