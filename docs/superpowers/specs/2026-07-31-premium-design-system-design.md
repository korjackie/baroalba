# 바로알바 프리미엄 디자인 시스템 — 설계 (2026-07-31)

> 목표: 화면마다 제각각인 시각 규칙을 하나의 시스템으로 좁혀, 앱 전체가 한 사람이 만든

## 1. 배경 — 왜 지금 "저렴해 보이는가"

`assets/css/style.css` + `바로알바.html` + `assets/js/app.js` 3파일 실측 (2026-07-31):

| 축 | 현재 | 프리미엄 앱 기준 |
|---|---|---|
| 색 | **고유 362종**, 리터럴 4,548회 vs 토큰 741회 (채택률 14%) | 회색 4~5 + 강조 1 + 상태 2~3 |
| 글자 굵기 | **7종** (300~900). 800이 564회, 900이 284회 | 3~4종 |
| 글자 크기 | 27종 | 6~7종 |
| 모서리 | 23종 | 3~4종 |
| 그림자 | **82종** | 2~3종 |

**1순위 원인은 굵기다.** 800·900이 848회로 전체의 절반 가까이다 — 거의 모든 글자가 굵다.
전부 강조하면 강조가 사라지고, 위계 없이 시끄러운 화면이 된다.

**2순위는 회색 8단계**(`#111 #222 #333 #555 #666 #888 #aaa #bbb`, 약 1,350회)와
밝은 회색 5종(약 700회)이다. 같은 역할에 매번 다른 값을 써서 화면 간 규칙이 안 맞는다.

디자인 토큰(`--ink-900/600/400/200`, `--line`, `--surface-2`, `--r`, `--r-sm`)은
2026-07-27에 이미 정의됐으나 절반만 적용된 상태다. **이 작업은 새 시스템을 만드는 게
아니라, 이미 정의된 시스템을 앱 전체에 관철시키는 것이다.**

## 2. 방향 — "절충안" (대표님 확정, 2026-07-31)

세 방향 중 선택:

| 방향 | 내용 | 판정 |
|---|---|---|
| 미니멀 | 여백 크게, 정보량 축소 | ❌ 한 화면 공고 수가 줄고 시니어에게 작게 느껴짐 |
| **절충** | **굵기만 정리, 글자크기·정보량 유지** | ✅ **채택** |
| 가독성 우선 | 글자를 더 키우고 대비 강화 | ❌ 프리미엄과 반대 방향 |

**이 앱은 외국인·시니어 특화를 지향**하므로(2026-07-29 확정), 전형적인 프리미엄
미니멀(얇은 글씨·넓은 여백)은 타겟 사용자의 가독성과 충돌한다. 굵기의 **상대 위계**만
정리하고 글자 크기와 정보 밀도는 건드리지 않는다.

## 3. 적용 방식 — 축 단위 순차 (대표님 확정)

화면 단위(홈→지도→상세…)가 아니라 **축 단위**로 앱 전체에 일괄 적용한다.

- **화면 단위의 문제**: 작업 중 "새 화면 반 / 옛 화면 반"이 되는데, 이 앱은
  홈↔지도↔상세 전환이 잦아 그 불일치가 즉시 드러난다.
- **축 단위의 이점**: 매 단계가 전역이라 앱은 항상 일관된 상태를 유지한다.
  각 축이 독립 커밋이라 롤백 단위가 명확하다.

순서와 근거:

| 차수 | 축 | 근거 |
|---|---|---|
| 1차 | 글자 굵기 | 체감 변화가 가장 크고, 색을 안 건드려 위험이 낮다 |
| 2차 | 색 (회색·면·선) | 건수가 가장 많고 문맥 분기가 필요해 단독 배포 |
| 3차 | 모서리 · 그림자 | 시각적 마감. 1·2차가 안정된 뒤 |
| 4차 | 간격 (4/8 그리드) | 레이아웃이 움직이므로 마지막. **별도 계획으로 분리**(4-4절) |

**이번 구현 범위는 1~3차다.**

## 4. 축별 상세 설계

### 4-1. 1차 — 글자 굵기 (7종 → 4종)

상대 순서를 보존한 채 전체를 한 단계씩 내린다. 위계는 유지되고 화면만 조용해진다.

| 현재 | 사용횟수 | → 신규 | 역할 |
|---|---|---|---|
| 900 | 284 | **700** | 제목 · 시급 · 로고 |
| 800 | 564 | **600** | 부제 · 버튼 · 배지 |
| 700 | 552 | **500** | 메타 · 본문강조 |
| 600 | 108 | **500** | 〃 |
| 500 | 22 | **400** | 본문 |
| 400 | 17 | **400** | 〃 |
| 300 | 6 | **400** | 〃 (300은 한글에서 너무 얇다) |

최종 스케일: **400 본문 / 500 보조강조 / 600 강조 / 700 제목**

600과 700이 500으로 합쳐지는 것이 유일한 정보 손실이나, 600은 108회뿐이라 영향이 작다.

**주의**: `font-weight: bold`(=700), `bolder`, 숫자 없는 표기가 있는지 먼저 확인하고
있으면 함께 매핑한다.

### 4-2. 2차 — 색

#### 텍스트 (회색 8단계 → 4단계)

| 현재 리터럴 | 횟수 | → 토큰 | 값 |
|---|---|---|---|
| `#111` `#222` `#15181E` | ~280 | `--ink-900` | `#15181E` |
| `#333` `#555` `#4E5661` | ~288 | `--ink-600` | `#4E5661` |
| `#666` `#888` `#838C98` | ~308 | `--ink-400` | `#838C98` |
| `#aaa` `#bbb` | **474** | `--ink-400` | `#838C98` |

**`#aaa`·`#bbb`(474회)를 한 단계 진하게 올리는 것이 이번 안의 핵심 판단이다.**
대비가 올라가 **시니어·외국인 가독성이 함께 개선**된다. 실측 결과 `#bbb` 154회가
**전부 `color:` 용도이고 `border:` 사용은 0건**이라 통합해도 선이 두꺼워 보이는
부작용이 없다.

`--ink-200`(`#C3CAD3`)은 비활성·플레이스홀더 전용으로 남긴다.

#### 면·선 (밝은 회색 5종 → 3종)

| 현재 | 횟수 | → 토큰 | 값 |
|---|---|---|---|
| `#fff` | 659 | `--surface-0` | `#FFFFFF` (카드·시트) |
| `#f5f5f5` `#f8f8f8` | 233 | `--surface-1` **(신설)** | `#F4F6F8` (페이지 배경) |
| — | — | `--surface-2` (기존) | `#FBFCFD` (중립 칩) |
| `#eee` `#f0f0f0` `#e5e7eb` | 457 | `--line` | `#E3E7EC` (테두리·구분선) |

**`--surface-1` 신설 이유**: 기존 `--surface-2`(`#FBFCFD`)는 거의 흰색이라
페이지 배경으로 쓰면 흰 카드가 배경과 분리되지 않는다. 페이지 배경용 단계가 별도로 필요하다.

#### 🔴 문맥 분기 필수

실측: **`#f0f0f0`은 `border`로 106회, `background`로 49회 사용된다.**
같은 리터럴이 두 역할을 겸하고 있으므로 **단순 문자열 치환은 금지**한다.
치환 스크립트는 속성명을 함께 읽어 분기해야 한다.

```
border-color / border / border-* : #f0f0f0 #eee #e5e7eb  →  --line
background / background-color    : #f0f0f0 #eee #e5e7eb  →  --surface-1
```

#### 🔴 정정 (2026-07-31, 1차 배포 후 재실측)

착수 전에는 `#f0f0f0`만 측정했으나, 9개 대상 파일 전체로 5종을 다시 재보니
**위 매핑표가 부정확했다.**

| 리터럴 | 총 | border | background | 기타 |
|---|---|---|---|---|
| `#eee` | 167 | 134 | 17 | 16 |
| `#e5e7eb` | 148 | 90 | 22 | **36** |
| `#f0f0f0` | 185 | 113 | 51 | 21 |
| `#f5f5f5` | 150 | **39** | 94 | 17 |
| `#f8f8f8` | 96 | 2 | 90 | 4 |

- **`#f5f5f5`를 "면"으로만 분류한 것은 틀렸다** — border로 39건 쓰인다. 그대로
  `--surface-1`로 치환하면 **선이 배경색이 되어 사라진다.**
- 따라서 문맥 분기는 `#f0f0f0` 한 종이 아니라 **5종 전부에 적용**해야 한다.
- **"기타" 94건**(그라디언트 정지점, `box-shadow` 색상 인자, SVG `fill`/`stroke`,
  `outline` 등)은 속성명만으로 역할을 판정할 수 없다. **자동 치환 대상에서 제외하고
  목록을 뽑아 눈으로 확인**한다.

수정된 규칙:

```
border* 속성값       →  --line
background* 속성값   →  #f5f5f5·#f8f8f8 이면 --surface-1
                        #eee·#f0f0f0·#e5e7eb 이면 --surface-1
그 외(기타 94건)     →  자동 치환 제외, 목록 출력 후 개별 판단
```

#### 예외 — 절대 건드리지 않는 색

| 색 | 횟수 | 이유 |
|---|---|---|
| `#C8102E` (`--red`) | 92+ | 브랜드 아이덴티티 |
| `#FEE500` | 9 | 카카오 브랜드 규정 |
| `#03C75A` | 4 | 네이버 브랜드 규정 |
| `#4285F4` | 3 | 구글 브랜드 규정 |
| `#22c55e` `#16a34a` `#10B981` | 45 | **on/off 토글·상태점.** 2026-07-29(Phase 74)에 "on/off 관례라 그대로 둔다"고 이미 판단한 사항 |
| `--fnb` `--logistics` `--sales` `--cleaning` `--event` | — | 지도 마커 카테고리 구분용. 정보를 나르는 색이라 이번 범위 밖 |

### 4-3. 3차 — 모서리 · 그림자

#### 모서리 (23종 → 4종 + pill)

| 신규 토큰 | 값 | 용도 | 흡수하는 기존 값 |
|---|---|---|---|
| `--r-sm` (기존) | `8px` | 칩 · 작은 버튼 | 2, 4, 6, 8, 9 |
| `--r` (기존) | `12px` | 카드 · 입력 | 10, 12 |
| `--r-lg` **(신설)** | `16px` | 큰 카드 · 패널 | 14, 15, 16 |
| `--r-xl` **(신설)** | `20px` | 시트 · 모달 | 20, 24 |
| — | `999px` | pill | 유지 |

#### 그림자 (82종 → 3종)

```css
--shadow-sm: 0 1px 3px rgba(21,24,30,.06);    /* 카드 */
--shadow-md: 0 2px 8px rgba(21,24,30,.08);    /* 검색바 · 떠있는 요소 */
--shadow-lg: 0 8px 24px rgba(21,24,30,.12);   /* 모달 · 시트 · FAB */
```

**순검정 `rgba(0,0,0,…)` → 잉크색 기반 `rgba(21,24,30,…)`으로 바꾸는 것이 핵심이다.**
순검정 그림자는 화면을 탁해 보이게 한다. 또한 현재 82종이 제각각이라 요소마다 떠 있는
높이가 안 맞는데, 3단계로 좁히면 계층이 일관되게 읽힌다.

### 4-4. 4차 — 간격 (4/8 그리드)

`--sp-1:4px --sp-2:8px --sp-3:12px --sp-4:16px --sp-5:20px --sp-6:24px --sp-7:32px`

레이아웃이 실제로 움직이는 유일한 축이라 마지막에 둔다. 1~3차가 안정된 뒤
**화면별 육안 확인과 함께** 점진 적용한다 — 이 축만은 전역 기계 치환을 하지 않는다.

⚠️ **4차는 이번 구현 계획에 포함하지 않는다.** 1~3차는 "문맥 인식 기계 치환"이라
하나의 계획으로 묶이지만, 4차는 화면별 판단이 들어가는 성격이 달라 별도 스펙·계획으로
분리한다. 1~3차 배포가 안정된 뒤 재스코핑한다.

## 5. 작업 절차 (매 차수 공통)

1. **치환 스크립트 작성** — Node 스크립트, 문맥(속성명) 인식, 예외 목록 반영
2. **드라이런** — 치환 건수와 예외 적중 건수를 먼저 출력해 확인.
   **판정 기준은 4절 매핑표의 실측 건수다** (예: 1차라면 `900→700` 284건,
   `800→600` 564건). 표와 10% 이상 어긋나면 스크립트에 문제가 있는 것이므로 중단하고
   원인을 찾는다 — 그대로 적용하지 않는다
3. **적용** → `node --check` 3파일(`app.js` `sw.js` `shared-lang.js`)
4. **락스텝 5곳 동기화** — `app.js`의 `_APP_V` / `sw.js`의 `CACHE` /
   `바로알바.html`의 `?v=` 4개(shared-lang·style.css·app.js·app_ui.js)
5. **단독 커밋** — 축 1개 = 커밋 1개 (롤백 단위)
6. **푸시 → 라이브 `sw.js` 버전 확인.** 5분 넘게 안 바뀌면 `vercel --prod --yes` 수동 배포
   (2026-07-28에 웹훅 누락 사례 있음)
7. **실기기 확인** — 홈 / 지도 / 공고상세 / 마이페이지 / 업주 공고관리 5화면

## 6. 검증

- **문법**: `node --check` 3파일 (기존 규칙)
- **치환 정확도**: 드라이런의 예외 적중 건수가 4-2절 예외표와 일치하는지 대조
- **잔여 리터럴**: 각 차수 후 해당 축 리터럴이 예외 목록만 남았는지 재실측
  (예: 1차 후 `font-weight:800` 잔여 = 0)
- **시각**: 실기기 5화면 스크린샷. 필요 시 Playwright 390px 실측
  (Phase 65·67에서 쓴 방식 그대로)

## 8. 범위 밖 (YAGNI)

- **기능·문구·레이아웃 변경** — 이번은 순수 시각 작업
- **인라인 스타일의 CSS 클래스 이전** — `app.js` 전면 수술이라 위험 대비 실익이 낮다.
  토큰 참조로 바꾸는 것만으로 목표(일관성)는 달성된다
- **다크 모드** — 이 앱은 다크 테마를 설계한 적이 없고 `color-scheme:light`로
  명시 고정했다(Phase 66)
- **브랜드 레드·로고 변경** — 대표님이 "브랜드 전체 재정의"를 선택하지 않았다
- **모션·트랜지션** — 별도 축. 1~4차 완료 후 재평가
- **글자 크기 27종 정리** — 절충안 선택에 따라 크기는 유지한다. 다만 4차 이후
  극단값(9px 이하 등)만 별도 검토

## 9. 미결 — 착수 전 확인할 것

- `font-weight: bold` / `bolder` 등 숫자 아닌 표기의 존재 여부와 건수
- `#eee` · `#e5e7eb`의 border/background 문맥 분포 (`#f0f0f0`은 106/49로 측정 완료)
- `index.html` · `login.html` · `admin.html` 등 **독립 HTML 포함 여부** —
  이 파일들은 앱 CSS를 안 쓰므로 전역 처리가 자동으로 따라오지 않는다(Phase 68-B 교훈).
