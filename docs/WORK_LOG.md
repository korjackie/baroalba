#### 발견된 근본 원인 패턴 (반복적으로 나타난 것)

이번 세션에서 가장 많이 반복된 버그 패턴은 **"존재하지 않는 함수를 호출하고 있었다"**
는 것이었다.

- `openBottomSheet()` / `closeBottomSheet()` — 바로스팟 "이용권 구매" 버튼이 호출하고
  있었으나 코드 어디에도 정의된 적이 없었음. 원본부터 있던 버그.
- `showCustomConfirm()` — 바로스팟/바로미팅 신청 확인창이 호출했으나 미정의.
  이미 존재하던 `showConfirmDialog()`로 교체.
- `cancelLang()` / `saveLang()` / `selectLang()` — 실제로는 `shared-lang.js`에 정상
  구현되어 있었음(v371에 이미 고쳐짐). 이 셋은 버그가 아니라, 업주 계정 쪽에 이
  화면 자체의 HTML이 없었던 것이 진짜 원인.

즉 "버튼이 눌러도 반응이 없다"는 증상은 매번 원인이 달랐다 — ①함수 자체가 없거나,
②함수는 있지만 실제 DB 반영 로직이 없거나(바로미팅 신청이 토스트만 뜨고 아무것도
저장 안 하던 것), ③애초에 화면(HTML)이 없거나. 셋 다 "캐시 문제"로 오인하기 쉬운
증상이라 주의가 필요하다.

#### PWA 캐시 버전에 대한 별도 발견

`바로알바.html`의 `V`, `app.js`의 `_APP_V` / SW 등록 쿼리, `sw.js`의 `CACHE` 키 —
이 세 곳이 동일한 버전 번호로 동기화되어야 클라이언트가 서비스워커 캐시를 강제로
비우고 새 코드를 받는다. 10건 넘는 커밋이 있었음에도 이 번호(381)가 전혀 갱신되지
않고 있었던 것을 발견 — 즉 이번 세션 이전의 여러 수정사항이 실제 사용자 기기에는
전달되지 않고 있었을 가능성이 있다. 381→384로 올리며 이후로는 기능 변경이 있을
때마다 세 곳을 함께 올리는 것으로 프로세스를 바꿈.

#### 발견된 근본 원인 패턴 (이 구간의 핵심)

이번 구간에서 반복해서 나타난 패턴은 **"스키마 드리프트 — 코드는 특정 컬럼을
조회하는데 실제 DB엔 그 컬럼이 없어(이름이 바뀌었거나, DDL이 실행 안 됐거나) 쿼리가
조용히 400으로 실패하는 것"**이었다. 특히 위험했던 건 **에러 삼킴 패턴**이다:

```js
const { data } = await db.from('businesses').select('region, ...');
// error를 구조분해하지 않아 400이 나도 data=null로 조용히 넘어감 → 화면이 빈 채로 정상인 척
```

- **`businesses.region`** — 4개 화면의 select에 들어있었으나 실제 DB에 없는 컬럼. 관련 화면들이 빈 결과로 조용히 죽어있었음.
- **`businesses.plan`** — 결제 후 이 컬럼에 PATCH하는데 컬럼이 없어 400. 문서에 오래 있던 P0("plan이 free로 리셋")의 진짜 근본원인. 구독은 `subscriptions`에 정상 저장되지만 클라이언트는 `businesses.plan`을 읽어 항상 free로 보였던 것.
- **`applications.created_at`/`reviewed_at`** — 실제로는 `applied_at`/`employer_reviewed_at`. 관리자 통계·리뷰 표시가 죽어있었음.
- **`businesses.owner_id` + 잘못된 조인키** — admin에서 모임 주최자 이름이 항상 공란이던 원인. `host_id`(=kakao_uid)를 workers는 `id`로, businesses는 없는 `owner_id`로 조인. 스키마는 멀쩡한데 **키가 틀린 의미 버그**라 컬럼 존재검사만으론 못 잡음.
- **`coupons.ticket_count`/`used_count`/`max_uses_per_user`** — 실제로는 `pass_qty`/`uses_count`/(부재). 쿠폰 지급수 undefined, 카운터 안 오름, **1인당 재사용 제한이 전혀 안 걸려 쿠폰 무한사용** 가능했음.

#### 왜 "수차례 전면검수"에도 새어나갔나 — 원칙 13-9 확립

가장 중요한 산출물. "여러 번 전수검수 했는데 이상없다고 했던" 버그들이 반복해서
새어나간 이유는 **검수를 코드에 대고 했기 때문**이다. 코드 리뷰는 "이 컬럼이 실제
DB에 존재하는가"를 검증할 수 없다. 스키마 드리프트를 잡으려면 반드시 **살아있는
DB에 실제 쿼리를 날려(HTTP 200/400)** 컬럼 존재를 확인해야 한다.

```bash
# 컬럼 존재 검증 (200이면 존재, 400이면 없음)
curl -s -o /dev/null -w '%{http_code}' \
  "$SB/rest/v1/businesses?select=plan&limit=1" \
  -H "apikey: $ANON" -H "Authorization: Bearer $ANON"
```

이건 모델(소넷/오푸스)의 역량 문제가 아니라 **검증 방법론의 문제**다. 어떤 모델이든
코드만 읽으면 못 잡고, 살아있는 DB에 대조하면 잡는다. (13-8 "재해석 대신 복붙"에
이어 확립된 원칙.)

### 3-1. 기술전략 — React Native 전환 검토 (원본 `기술전략/바로알바_기술전략_260716.md`, 2026-07-16)

**원래 전략**: 웹/PWA → ①WebView 래핑으로 스토어 진입 → ②스케일업 시 React Native 재구축.

**검토 결과 (같은 날 코드를 직접 고치면서 확인)**:

- **Step 1 은 이미 끝나 있었다.** 문서는 "Capacitor/Ionic 으로 포장" 을 할 일로 적었지만 실제로는
  `MainActivity.java` 기반 **커스텀 네이티브 WebView 래퍼가 이미 동작 중**이었다 —
  `WindowInsetsCompat` 로 상태표시줄/키보드 높이를 CSS 변수(`--sat`/`--sab`)에 실시간 주입,
  FCM 토큰 처리, `onShowFileChooser`, `AndroidBridge` JS↔네이티브 브릿지, GitHub Actions APK
  빌드까지. 범용 Capacitor 보다 이 앱에 맞춰져 있어 갈아탈 이유가 없다.
  **남은 실질 과제는 "iOS 래퍼가 없다" 하나뿐.**
- **"푸시가 불안정" 은 Android 엔 해당 없음.** FCM + 서비스별 알림 토글(`workers.notify_*`)이
  서버 차단까지 구현돼 있다. **실제 갭은 iOS PWA 푸시 제약 하나.**
- **업계 사례**: 배민 사장님 앱은 Flutter, **배민커넥트(라이더 실시간 위치추적)는 React Native**
  (우아콘 2023). "실시간 위치 서비스 = 반드시 순수 네이티브" 라는 전제는 사실이 아니며,
  성능 이슈는 그때그때 네이티브 모듈로 보완하는 방식이 실무 표준이다.
- **전환 규모는 과소평가돼 있었다.** `바로알바.html` + `app.js` 에 2만 줄 이상이 컴포넌트 분리도
  상태관리 라이브러리도 없이 전역변수 + 인라인 핸들러로 짜여 있다. "프론트엔드만 갈아끼운다" 가
  아니라 **사실상 전면 재작성**이다. 백엔드(Supabase) 재사용 이점은 확실하지만 기간 단축 효과는 제한적.

**결론 (계속 유효)** — 지금 전환하지 않는다. 웹 기반의 **즉시 배포 속도**(하루에도 피드백을 받아
수 분 내 반영)는 초기 단계에서 가장 값진 자산이고, RN 으로 가면 스토어 심사 주기 때문에 영구히
잃는다. 전환 트리거는 "스케일업 시점" 같은 막연한 기준이 아니라 **못 견디는 구체적 갭(백그라운드
GPS, iOS 푸시)이 실제로 발생했을 때**로 잡는다. 그때도 전면 재작성보다 **해당 기능만 네이티브
모듈로 얹는 하이브리드로 얼마나 버틸 수 있는지 먼저 검토**한다. 실제로 전환을 결정하면 React
Native 는 배민커넥트 사례로 검증된 선택지이므로 그대로 채택해도 된다.
