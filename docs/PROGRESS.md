### ②-D ✅ 크롭 결과가 정사각으로 눌리던 것 (2026-08-04, v615)

`applyCrop()` 이 비율과 무관하게 **항상 400×400** 으로 뽑고 있었다. 1:1 로 자르는
화면(프로필·만남)은 우연히 맞았지만, **자유 비율을 쓰는 공고 사진은 잘라낸 영역이
정사각으로 눌려서 저장되고 있었다.** 1:1 케이스만 맞아떨어져서 오래 안 드러났다.

잘라낸 비율을 유지하고 **긴 변만 `_cropMaxSize` 로 맞추도록** 고쳤다. 원본보다 키우지는
않는다(작은 사진을 확대하면 흐려지기만 한다). `_cropMaxSize` 기본값은 400 이라
**기존 호출부 3곳(프로필·공고·만남)의 동작은 그대로**고, 모임만 1080 을 넘긴다.

가로로 긴 단체사진 대응도 함께:
- 모임 크롭은 **자유 비율**, 열면 **사진 전체가 이미 선택**돼 있다(`autoCropArea:1`)
- **"전체 사진 그대로 쓰기"** 버튼 추가(`cropSelectAll()`). 자유 비율일 때만 보인다
- 상세 사진 띠는 `aspect-ratio` 고정을 걷어내고 `object-fit:contain` + `max-height:52vh`
  로 바꿨다 — 어떤 비율이든 전체가 보인다. 목록 카드 썸네일은 격자 정렬을 위해 정사각 유지

⚠️ **원본 파일을 그대로 올리지는 않는다.** 휴대폰 사진은 5~15MB 라 업로드가 느려지고
목록도 무거워진다. 화각은 그대로 두고 긴 변만 줄여 내보내는 방식이다.

### ②-E 크롭 UI 를 데스크톱에서 아예 조작할 수 없던 것 + 전 화면 적용 (v616)

**대표님 신고: "데스크톱인데 드래그나 핀치가 안 된다."** 원인은 두 개가 겹친 것이고
**둘 다 v615 에서 내가 만든 것**이다.

1. `dragMode: 'move'` — 드래그가 **이미지를 미는** 동작이라 마우스로 영역을 그릴 방법이 없다
2. `autoCropArea: 1` — 크롭 박스가 사진 100% 라 **줄일 여백도, 잡을 손잡이도 없다**

→ `dragMode:'crop'` + `autoCropArea:0.8` + `guides:true` + `modal:true`.
점선 박스가 안쪽에서 시작해 네 모서리를 바로 잡을 수 있고, 사진 위를 끌면 새로 그려진다.
**"전체를 기본 선택"이 친절할 거라 생각했는데 조작 자체를 막았다** — 기본값을 꽉 채우면
조작 여지가 사라진다는 것을 놓쳤다.

**전 화면 적용**(대표님 요청 "다른 사진올리기 기능도 모두"):
- `openCropModal` 의 **기본 비율을 1 → NaN(자유)** 로 바꿨다. 이걸로 프로필·만남 사진이
  전부 자유 비율이 된다(둘 다 비율 인자를 생략하고 호출한다)
- 업체 사진의 **별도 모달**(`openBizCropModal`)도 같은 옵션으로 맞추고,
  `applyBizCrop` 의 **800×800 고정**도 비율 유지로 고쳤다(`applyCrop` 과 같은 결함이었다)
- **`addJobImages` 는 크롭이 아예 없었다** — 고른 파일을 원본째 담고 있었다.
  모임과 동일한 순차 크롭을 붙였다

⚠️ 자유 비율로 풀어도 표시는 안전하다 — 프로필 슬롯·헤더 아바타·만남 사진이 전부
`object-fit:cover` 라 가운데만 보이고 찌그러지지 않는다(적용 전 확인함).

⚠️ **서류·채팅 사진에는 크롭을 붙이지 않았다** — 자격증/비자(`onCertFileSelected`
·`onVisaDocSelect`·`uploadDoc`)는 문서 전체가 보여야 하고, 채팅 사진 4종은 크롭을
강제하면 대화 흐름이 끊긴다.

②`my_tickets` 가 `barospot_passes` 잔여를 읽도록 변경해 **두 화면이 같은 값을 보게** 함
③적립 실패 시 사용 이력을 되돌려 재시도가 막히지 않게 함.

적립 성별은 `coupons.gender` → 없으면 `workers.gender` 순으로 정한다. 둘 다 없으면
**쿠폰을 소진시키지 않고** 400.

⚠️ **그 400 이 가입화면 코드 입력 경로를 깨뜨릴 뻔했다(v611 에서 같이 수정).**
`_processReferralSignup()` 은 로그인 직후 발사되는데, **SNS 가입은 그 시점에 아직
`workers.gender` 가 없다**(성별 게이트가 막 뜬 참). 그런데 이 함수가 **시도 전에**
`pending_ref_code` 를 지우고 `referral_processed` 플래그를 박아서, 실패하면 코드가
영구 소실된다. 이제 404(아예 없는 코드)가 아닌 실패·네트워크 오류면 코드를 되살려
다음 앱 진입(=성별 입력 후)에 재시도한다.
**"실패하면 재시도"를 설계할 때는 재시도에 필요한 입력을 먼저 지우고 있지 않은지 볼 것.**

⚠️ 이건 Phase 87 의 "쿠폰 생성 400" 과 **다른 버그**다. 생성은 고쳐졌지만 **사용**이
비어 있었다. `coupon_redemptions` 는 지금도 0건이라 아무도 밟은 적이 없다 —
**"기능이 있다"와 "끝까지 연결돼 있다"는 다르다. 재화는 최종 차감 지점까지 따라갈 것.**

### ⑧ 쿠폰 배포 경로 — 코드 + QR 공유 (2026-08-02, v612)

**대표님 요청: 1회 무료를 쿠폰 발급 형태로, 쿠폰번호와 QR 두 가지로 뿌린다.**
QR 로 무료를 주는 경로는 **원래 없었다**(공고 QR = 공고 열기, 바로패스 QR = 현장 신원확인,
추천 링크 = 포인트). 오픈 프로모션 기간이라 "QR 로 들어와도 무료"였던 게 QR 덕분으로
보였던 것뿐이다. 이번에 실제 경로를 만들었다.

| 조각 | 내용 |
|------|------|
| 관리자 → 프로모션 쿠폰 관리 | 쿠폰마다 **[공유]** 버튼 → 코드·QR·링크 시트. 남은 수량(`max_uses - uses_count`) 표시, 코드/링크 복사, QR 이미지 저장, 카카오 공유 |
| 링크·QR 진입 | `…/바로알바.html?coupon=CODE` → `_processPendingCoupon()` 이 로그인 직후 자동 등록. **코드를 손으로 칠 필요 없음** |
| 서버 | 추가 작업 없음 — ⑦에서 고친 `/api/coupon` 이 그대로 적립 |

**지급 범위는 "로그인한 사람 모두"다**(대표님 결정). 추천코드(`?ref=`)와 달리 가입 후
5분 조건이 없다 — 매장 부착·전단지 용도라 기존 회원도 받아야 하고, 1인 1회는 서버의
`max_uses_per_user` 가 건다. **전체 배포량은 `max_uses` 로만 통제되므로, 링크가 단톡방에
퍼지면 한도가 순식간에 소진될 수 있다. 뿌리기 전에 한도를 반드시 정해둘 것.**

⚠️ QR 은 **로컬 `assets/js/qrcode.min.js`** 로 만든다(admin.html 에 스크립트 추가).
외부 QR 생성 API 를 쓰면 쿠폰 코드가 남의 서버 로그에 남는다.
링크는 `encodeURI('/바로알바.html')` 로 ASCII 화한다 — QR 스캐너가 원시 한글 바이트를
그대로 넘기면 브라우저에 따라 깨진 URL 이 열린다.

**실패 분류는 서버가 `retryable` 플래그로 알려준다.** 성별 미설정처럼 조건만 갖춰지면
성공할 실패만 코드를 남겨 재시도하고, "이미 사용·소진·없는 코드"는 버린다.
**한국어 에러 문구를 클라이언트가 문자열 비교하게 두지 말 것**(문구를 고치면 조용히 깨진다).

#### ⑧-B 홍보 포스터 → 랜딩 → 쿠폰 경로 (2026-08-03 연결 완료)

바로만남 홍보 포스터가 **"앱 설치 시 1회 무료 쿠폰 지급!"** 을 약속하는데,
**포스터 QR 은 쿠폰과 아무 상관이 없었다.** 실제 행선지는 `https://baromannam.vercel.app/`
(바로만남 소개 랜딩)이고, 그 랜딩의 앱 버튼은 쿠폰 없이 앱 루트만 가리키고 있었다.
**포스터를 뿌려도 받을 방법이 없는 상태였다.**

경로 전체:

```
포스터 QR  →  baromannam.vercel.app  →  baroalba.multimove.co.kr/?coupon=BARO-MANNAM-2026
             (서비스 설명 + CTA 3곳)      → 루트가 /바로알바.html 로 쿼리 보존 리다이렉트
                                          → app.js 가 로그인 직후 자동 등록
```

랜딩 소스는 **다른 저장소**다 — `korjackie/baromannam-landing`, 로컬은
`G:\내 드라이브\MultiMOVE\2. Projects\바로만남(antigravity)\index.html`(커밋 `560b56f`).
CTA 3곳(헤더 "앱으로 이동" · 본문 버튼 · 테스터 신청 자동응답 메일)에 코드를 실었다.
쓰는 쿠폰은 이미 있던 `BARO-MANNAM-2026`(이용권 1장 · 전체 한도 500 · 1인 1회 · 활성).

⚠️ **포스터 QR 자체는 바꾸지 않았다** — 이미 인쇄·배포됐을 수 있고, 랜딩이 서비스를
먼저 설명한 뒤 앱으로 보내는 편이 콜드 스캔에 낫다. **바꿔야 할 일이 생기면 QR 만
새로 만들지 말고 이 문단의 경로를 먼저 볼 것**(포스터·랜딩·앱이 서로 다른 저장소라
한 곳만 고치면 약속이 또 깨진다).

⚠️ 앱 루트(`/`)는 `lang` 을 뺀 쿼리를 그대로 `/바로알바.html` 로 넘긴다(실측 확인).
그래서 홍보 링크는 짧은 `…co.kr/?coupon=CODE` 를 써도 된다. **`lang` 은 지워지므로
다국어 랜딩에서 `?lang=` 과 같이 붙여 보내면 언어 지정이 사라진다.**

### 8-2. i18n 스윕 5차 — 토스트/알림 메시지 전수 번역 (2026-07-27, v576 완료)

"언어작업 다 끝났어?" 질문에 `grep -oE "showToast\('[가-힣][^']*'\)" assets/js/app.js | wc -l`로 실측했더니 하드코딩된 한국어 토스트가 155개(고유 127개) 남아있는 게 발견됨. 이어서 콤마 인자(지속시간)·문자열 연결(`+ error.message`)·템플릿 리터럴(`${var}`) 형태로 숨어있던 것까지 전수 조사해 총 4개 배치로 완료:

- **1배치**: `showToast('한국어')` 단순 리터럴 155건(고유 127개) — `tools/i18n/addkeys.py`로 `keys.json` 일괄 삽입 후 Python으로 `showToast('X')` → `showToast(t('key'))` 전수 치환
- **2배치**: `'접두사: ' + error.message` 연결형 + `'문구', 5000)` 지속시간형 48건(신규 31키) — 따옴표로 감싼 부분 문자열만 치환(`'저장 실패: '` → `t('toast_save_failed_prefix')`), `+ error.message` 등 동적 부분은 그대로 둠
- **3배치**: 템플릿 리터럴 안 `${var}` 보간 19건 + `showAlert` 1건(신규 17키, `_fmt` 접미) — `showToast(t('key').replace('{n}', val))` 형태로 전환
- **총 158개 신규 키 × 8개국어**, `node --check` 통과, 버전 576 동기화

**작업 중 겪은 실수와 교훈**: `addkeys.py`용 JSON에 여러줄 문구(`\n` 포함, 예: `toast_premium_pro_only`)를 담을 때 JSON 이스케이프(`\n`→실제 개행)와 JS 이스케이프(파일에 텍스트로 `\n` 두 글자가 남아야 함)를 혼동해서 `shared-lang.js`에 진짜 개행문자가 그대로 들어가 SyntaxError가 남. **JSON 소스에 `\\n`(백슬래시 두 개)로 적어야 JS 파일엔 `\n`(백슬래시+n 두 글자)로 남는다** — 다음에 이 도구 쓸 때 반드시 기억할 것. 잘못 삽입된 채로 한 번 실행했다가 `git checkout -- shared-lang.js`로 되돌리고 재실행함(당시 아직 커밋 전이라 안전하게 복구 가능했음).

**의도적으로 남겨둔 것**: `assets/js/app.js` 15887번째 줄 근처 스카우트 기능의 데이터 요약 문자열(`${biz_name} · ${title} · ${wage}원/${단위}`)에서 단위(건/시간)는 기존 키로 번역했지만 "원" 한 글자는 그대로 둠 — 복합 데이터 문자열이라 구조 전체를 바꾸지 않는 한 그 한 글자만 번역해도 실익이 적어 스킵. 이 외에 `showToast`/`showAlert` 기준으로는 전수 완료.

### Phase 87 ✅ `api/*.js` 전수 스키마 대조 3차 — 쿠폰 생성 400 + 신고 조인 (2026-08-02, 커밋 `3ac2ac8`)

Phase 59-B 가 *"남은 권장 작업"* 으로 남긴 서버함수 전수 대조를 **12개 파일 전부**에 수행했다.
감사 스크립트를 [`tools/schema-audit/audit_api.py`](../tools/schema-audit/audit_api.py) 로
저장소에 남겼다(`sb()` 헬퍼와 `fetch(.../rest/v1/...)` 직접호출 양쪽을 파싱, URL 컬럼 +
INSERT/PATCH 바디 키를 함께 대조). **컬럼참조 193건 존재확인, 드리프트 2건.**

**① 관리자 화면의 쿠폰 생성이 계속 400 이었다 (드리프트)**
실제 컬럼은 `pass_qty`/`uses_count` 인데 `admin.js` 의 `create_coupon` 은 `ticket_count` 와
**아예 없는 컬럼 `max_uses_per_user`** 로 INSERT 하고 있었다. **Phase 59-B 가 쓰는 쪽
(`coupon.js`)만 고치고 만드는 쪽을 놓친 사본**이다. `admin.html` 의 목록 표시도 같은 옛
이름(`c.ticket_count`/`c.used_count`)이라 **지급 장수는 항상 "1장", 사용 횟수는 항상 "0회"**
로 보이고 있었다. 1인당 사용 제한은 컬럼 자체가 없어 `coupon.js` 가 `|| 1` 로 방어 중이다
(=항상 1회). 진짜로 열려면 DDL 이 필요해서 이번엔 보내지 않는 쪽으로 정리했다.

**② 신고 목록·신고 메일의 사람 이름이 항상 UUID 앞 8자리 (조인 의미버그, 세·네 번째 사본)**
`reports.reporter_id`/`target_id` 는 `workers.id` 가 아니라 **kakao_uid(=auth uid)** 다
(`app.js` 가 `reporter_id: currentUser.id`, `openReportModal('user', uid)`,
`openOwnerReport('worker', w.kakao_uid)` 로 넣는다). 그런데 `api/admin.js` 의 신고목록과
`api/email.js` 의 신고 알림 메일이 **둘 다 `workers.id` 로 조인**하고 있었다.
`target_type='worker'` 는 조회 대상에서 아예 빠져 있기도 했다. 옛 데이터 대비로
`kakao_uid`·`id` 두 키 모두로 찾도록 고쳤다(`or=(kakao_uid.eq.X,id.eq.X)` — 라이브 검증함).
신고 메일은 모임 신고도 `사용자` 로 표기하던 것까지 함께 정리.

⚠️ **이 유형은 스키마 대조로 절대 안 잡힌다** — 컬럼이 양쪽 다 존재하므로 감사는 무조건
통과한다. 저장하는 쪽 코드에서 **그 값이 무엇인지 역추적**해야 발견된다. **전례가 이미
네 번**(Phase 59-B 모임 주최자, 이번 2건 포함)이라 CLAUDE.md 13-9 에 별도 항목으로 박았다.

**③ 감사 방법론 정정 — 401을 "판정 불가"로 넘기면 안 된다**
`workers` 에 anon **컬럼 단위 grant** 가 걸려 있다(name·age·bio·rating 등 공개 필드만 허용,
`kakao_uid`·`phone`·`last_lat`·`referral_code` 등은 401). 처음엔 `select=*` 이 401 이라
`workers`·`applications`·`chat_rooms` 를 통째로 "판정 불가"로 건너뛰었다. 그런데
**PostgreSQL 은 이름 해석을 권한 검사보다 먼저** 하므로 없는 컬럼은 권한과 무관하게
42703(400)이 온다 — 즉 **401/42501 도 "컬럼 존재 확정"** 이다. 이걸 바로잡고 나서야
26건이 감사 범위에 들어왔다. 판정표는 CLAUDE.md 13-9 참고.

**④ 감사 스크립트 자체의 결함 2건 (같은 날 발견·수정, 커밋 `cb024e3`)**
저장소에 넣은 `audit_api.py` 를 검증하다가, `JSON.stringify({` 오프셋 조건이 틀려
**쓰기 바디 키를 통째로 건너뛰고 있던 것**을 발견했다. 즉 첫 실행의 *"10개 서버함수
깨끗"* 은 **URL 컬럼만 본 결과**였다(위 ①번 쿠폰 드리프트도 이 도구가 아니라 별도
스크립트로 잡은 것이다). 고치고 나니 이번엔 600자 윈도우가 다음 호출까지 넘어가
오탐 12건이 났다 — `workers` GET 뒤에 이어지는 `notifications` INSERT 바디를 workers
컬럼으로 오인하는 식. **호출 경계로 자르고 `method` 가 POST/PATCH/PUT 인 경우에만**
바디를 붙이도록 조였다. 재실행 결과 **컬럼참조 185 → 232건, 존재확인 240건 / 없음 0건**

**음성 대조**해 검출되는 것까지 확인했다.
→ 교훈: **감사 도구는 "통과"가 아니라 "일부러 심은 버그를 잡는지"로 검증해야 한다.**
   0건은 깨끗하다는 뜻일 수도, 아무것도 안 보고 있다는 뜻일 수도 있다.

**⑤ 쿠폰 1인당 사용 제한 활성화 (같은 날, 대표님 DDL 실행)**

### Phase 84 ✅ app_admins 보안 적용 + 그 여파 수습 + 설치배너 폭·겹침 (2026-08-01, v608, 커밋 `ceec5a8`)

#### 🔴 보안 — `app_admins` 잠금 실행 완료 (대표님 실행)

Phase 81 이 *"긴급 SQL 이 작성만 되고 실행이 안 됐다"* 고 보고한 건을 이 날 실행했다.

| 검사 | 실행 전 | 실행 후 |
|------|---------|---------|
| 공개 anon 키로 명단 조회 | 🔴 200, **관리자 이메일 4건 노출** | ✅ 401 |
| 공개 anon 키로 명단 INSERT | 🔴 가능(아무나 관리자 등록) | ✅ 401 |
| `is_app_admin()` 함수 | 🔴 없음(폴백 경로로만 동작) | ✅ 존재 + anon 실행 차단 |

**추가로 정책 SQL 한 번 더 실행했다.** 테이블을 잠그면 관리자 본인도 명단을 못 읽어
관리 화면(목록/추가/삭제)이 401 이 되기 때문이다.
```sql
grant select, insert, update, delete on public.app_admins to authenticated;
create policy app_admins_manage on public.app_admins
  for all to authenticated
  using (public.is_app_admin()) with check (public.is_app_admin());
```
→ **관리자에게만** 명단이 보이고 비로그인·일반 사용자는 여전히 차단(실측 401 재확인).

잠그는 순간 그 조회가 401 이 되어 배너가 안 떴다. 명단을 읽는 대신
`rpc('is_app_admin')` 로 boolean 하나만 물어보게 바꿨다(`admin.html:1046` 과 동일).
함수가 없는 환경에서는 예전 조회로 폴백한다.

검색**할 것. 이번엔 `grep -rn "app_admins"` 를 잠근 뒤에야 돌렸고, 그래서 배너가
사라진 걸 대표님이 먼저 발견했다.

#### 설치배너("로그인" 검은 바) 폭·겹침

대표님이 우측에 삐져나온 것으로 지목한 **분홍 원형 버튼**은 앱 요소가 아니다.

**착수 계기**: 인계 ③-3 교훈("독립 HTML은 `style.css`를 안 읽으니 `var()`가 미정의면
선언이 통째로 무효")을 **문장으로 남기는 대신 스크립트로 전수 검증**했다. 그랬더니
그 교훈이 예측한 유형이 실제로 걸렸고, 검증 과정에서 성격이 다른 버그 3건이 더 나왔다.

**검증 방법 — 이게 이번의 핵심.** 13-9("코드 말고 살아있는 것에 대고 검수하라")를
DB가 아니라 **CSS에 적용**했다. CSS는 문법이 틀려도 에러를 내지 않고 **그 선언만
조용히 버린다** — `.from()` 에러를 삼키는 패턴과 정확히 같은 실패 방식이라, 코드를
읽어서는 "이 선언이 실제로 먹었는지"를 확정할 수 없다. 그래서 **헤드리스 크롬으로
`getComputedStyle` 계산값을 찍어서 확인**했다. 추정으로 고친 것은 하나도 없다.

```bash
# 실제로 쓴 검증 (Chrome 은 이미 깔려 있다)
chrome --headless --dump-dom --allow-file-access-from-files test.html
#  → test.html 이 style.css 를 link 하고 getComputedStyle 결과를 DOM 에 써두면
#    파싱된 규칙 수 · 최종 계산값을 그대로 받아볼 수 있다
```

**① `admin.html` — `--ink-200`만 토큰 사본에서 누락 (인계 ③-3이 예측한 그 유형)**

`style.css`는 잉크를 900/600/400/**200** 네 단계로 정의하는데 사본엔 셋뿐이었다.
`.list-arrow`(관리자 메뉴 17행의 `›`)·`.close-btn:disabled`·인라인 2곳의 `color`가
무효가 되어 **상속색(검정)**으로 떴다. 특히 비활성 마감버튼은 배경만 회색이 되고
**글자는 빨강 그대로**라 눌리는 것처럼 보였다. Phase 78에서 아이콘을 SVG로 통일해놓고
바로 옆 화살표만 검정으로 튀던 상태였다.

**② `style.css` — `.toast` 규칙이 두 벌이고, 이기는 쪽이 망가진 쪽이었다 (앱 본체)**

914줄 규칙은 제대로 돼 있는데 1319줄에 **같은 선택자가 또 있어** 나중 선언이 이겼다.

- **`calc`는 `+`/`-` 양쪽에 공백이 필수다.** `calc(var(--nav-h)+20px)`는 무효 —
  실측하면 84px이 아니라 **`auto`**다. 토스트가 네비 위가 아니라 **정적 위치**에 떴다.
- `white-space:nowrap`이 위 규칙의 `pre-line`/`max-width:80vw`를 덮어써서, **i18n 5차에서
  넣은 `\n` 포함 토스트**(`toast_premium_pro_only` 등 8개 언어)가 한 줄로 화면 밖까지 흘렀다.

중복을 지우고 `z-index:20000`만 위 규칙으로 옮겼다(오버레이 8700 위에 떠야 함).
**⚠️ 이건 디자인 스윕 회귀가 아니다** — 6월 `backup/바로알바.html:1219`에도 같은 형태가
있는 **오래된 잠복 버그**다. 스윕을 의심했다가 백업 대조로 정정했다.

**③ `worker.html` — `theme-color`에 `var()`가 들어가 있었다**

`<meta name="theme-color" content="var(--red)">` — **meta의 content에서는 CSS 변수가
해석되지 않는다.** 파싱 실패로 무시되어 브랜드 빨강이 안 먹었다. 색 스윕(Phase 75)이
리터럴을 일괄 치환하며 meta까지 건드린 것으로 보인다. `#C8102E`로 되돌렸고, **다른
파일은 전부 리터럴이라 이 한 곳뿐**임을 전수 확인했다.

**④ `worker.html` — 2장 단기 목록에 남아있던 3종 점검 완료**

`color-scheme`/`viewport-fit`/안전영역이 **통째로 없었다**. `admin.html` 패턴을 그대로
복붙(규칙 7)해 `--sat`/`--sab` 추가, 헤더 `padding-top`, 하단 네비 `--sab` 반영.
`.content`도 ②와 같은 공백없는 `calc`라 **`padding-bottom`이 0px**이었고(실측),
마지막 카드가 하단 네비에 가리고 있었다.

**검증 결과 (전부 헤드리스 크롬 계산값)**

| 항목 | 수정 전 | 수정 후 |
|------|---------|---------|
| `style.css` 파싱 규칙 수 | — | 597개 정상 |
| `.toast` 규칙 개수 | 2벌(중복) | 1벌 |
| 앱 토스트 `bottom` | `auto` | `84px` |
| 앱 토스트 `white-space` | `nowrap` | `pre-line` (+ `max-width:80vw`) |

`node --check` 통과, 락스텝 6곳 604→605, 라이브 반영 확인(sw.js·`?v=`·admin·worker 전부).

**남은 판단거리**: `worker.html`은 **저장소 어디에서도 링크되지 않는 고아 페이지**다

**교훈 — 13-9를 CSS로 확장할 것.**
DB만 "살아있는 것에 대고 검수"할 대상이 아니다. **CSS도 틀린 선언을 조용히 버리므로
같은 부류다.** 앞으로 색·간격·레이아웃을 손대면 코드를 읽어 확인하지 말고
**계산값을 찍어라.** 특히 이 셋은 눈으로 안 잡힌다:
1. `calc()`의 `+`/`-` 양쪽 공백 (없으면 선언 전체가 죽는다)
2. 같은 선택자가 파일 안에 두 벌 있는지 (나중 것이 이긴다)
3. 독립 HTML의 `var()` 미정의 (`:root` 사본은 style.css와 자동으로 안 맞춰진다)

### Phase 79 ✅ 지원 직후 프로필 유도 + 간격 리듬 정리 (2026-07-31, v603~v604)

#### 지원 직후 프로필 채우기 유도 (v603, 커밋 `fff81e2`)

Phase 77에서 실측한 프로필 공백(9개 항목 평균 1.0개, 34/40명이 0~1개)에 대한 대응.

③업주의 작성 요청이었는데, **라이브 공고가 0건이고 지원 활동 자체가 적은 상황에서
게이트를 걸면 남은 활동마저 죽는다.** 지원이 끝난 뒤에 띄운다 — 방금 지원했으니
"뽑히고 싶은 동기"가 최고조인 타이밍이기도 하다.

- 비어 있는 항목이 **3개 이상일 때만**, **하루 한 번만**. 매번 뜨면 그때부터는
  내용이 아니라 그냥 닫는 버튼이 된다
- 무엇이 비었는지 칩으로 보여주고 프로필 편집으로 직행
- 유도는 부가기능이라 실패해도 지원 플로우를 안 막게 `try/catch` 로 격리
- 신규 키 12개 × 8개 언어 = 96개

#### 5차 간격 — 2px 그리드 (v604, 커밋 `98e6146`)

**🔴 설계문서에 적어둔 "4/8 그리드"가 틀렸다는 걸 착수 실측에서 확인했다.**
`gap` 의 **53%가 4의 배수가 아니고** 최다값이 **6px(153)·10px(97)** 이다.
8px 로 올리면 칩이 넓어져 **줄바꿈이 터지고**, "정보 밀도를 유지한다"는 절충안
방향과도 정면으로 어긋난다 — 4/8은 여백을 키우는 체계라 미니멀 쪽 도구다.

**이 앱의 실제 리듬은 2px 단위다.** 6·10·14가 많은 건 우연이 아니라 한국어
모바일의 높은 밀도에서 자연스러운 값이기 때문.

2px 기준으로는 이상치가 **홀수값뿐**(4,600개 중 591개, 13%). 그중 **553건을
한 단계 줄이는 방향으로만** 정리 — 늘리면 넘치지만 줄이면 그럴 일이 없고
1px 차이라 눈에 띄지도 않는다. `--sp-1~11` 토큰 정의.

⚠️ 제외: `1px`(38건, 배지 미세조정이라 0px면 붙어버림), 음수(`-5px→-4px` 는
"덜 튀어나옴"이라 의도가 바뀜), `border-radius`(3차에서 처리됨).

⚠️ **치환 스크립트가 선언부를 재조립하면 안 된다** — 공백·포맷이 미묘하게 바뀐다.
값 앞부분은 원문 그대로 두고 뒤의 값만 갈아끼울 것.

**교훈**: 스펙에 적은 그리드 체계를 **착수 전 실측으로 검증**해야 한다. 업계 관행

**고친 것** — 랜딩과 같은 형태로 두 경로 신설. 기존 `selectLang()`/`saveLang()` 을
그대로 재사용해 새 로직은 없다(규칙 7).
- **앱 헤더에 지구본 + `<select>`**(`#header-lang-wrap`). **게스트일 때만 노출** —
  로그인 사용자는 그 자리에 알림 종이 오고 마이페이지 경로가 따로 있어 중복을 피함
- **`profile-guest` 에 "🌐 앱 언어" 행** 추가 — 설정을 찾으러 가는 사람을 위한 두번째 경로

**곁다리로 잡은 기존 버그**: 라벨 갱신이 `saveLang()` 안에만 있어서, **저장된 언어로
앱을 켜면 화면은 네팔어인데 마이페이지 "앱 언어" 값만 '한국어'** 로 남아 있었다.
`_syncLangLabels()` 로 분리해 **`applyLang()`** 에서 부르게 함(초기 로드·언어 변경
양쪽에서 호출되는 지점). 헤더 select 값도 함께 동기화해 두 컨트롤이 서로 다른 언어를
가리키는 상태를 막는다.

⚠️ `saveLang()` 이 `closeMpSub()` 를 무조건 부르는데, 헤더에서 호출하면 패널이 안 열린

### Phase 73 ✅ 근로계약서·지원서 PDF가 백지로 저장되던 문제 (2026-07-30, v596)

대표님 제보 — "합격한 사람의 근로계약서 PDF를 받았는데 파일에 아무 내용이 없다."
파일은 정상 생성되고 페이지 크기도 A4로 맞는데 안이 비어 있었다.

**원인** — `_downloadPdf()`(app.js)가 화면에 안 보이게 하려고 소스 div에 직접
`position:fixed;left:-9999px`를 줬는데, html2pdf는 소스를 **복제해 자기 오버레이에
넣으면서 `position`만 `relative`로 덮어쓴다**(번들 소스에서 확인:
`container.firstChild.style.position="relative"`). `left:-9999px`는 그대로 남아서
복제본이 `position:relative + left:-9999px`가 되고, 캔버스 원점 기준 9999px 왼쪽으로
밀려나 렌더 영역 밖으로 나갔다. 그래서 종이 크기는 맞고 내용만 없는 PDF가 나온 것.

**수정** — 화면에서 숨기는 역할을 바깥 래퍼(`holder`)로 옮기고, html2pdf에 넘기는
div에는 위치 오프셋을 일절 남기지 않았다. 복제 대상은 이 div뿐이라 오프셋이 따라가지 않는다.

`_downloadPdf`를 쓰는 경로가 두 개(`printContract` 근로계약서, `printWorkerProfile`
지원서)라 **둘 다 같이 고쳐졌다**. 2026-07-19에 인쇄→저장 방식으로 바꾼 이후로
줄곧 백지였을 것으로 보인다(그 전 `_printInPage` 인쇄 경로는 이 버그와 무관).

**교훈** — 라이브러리에 DOM 엘리먼트를 넘길 때, 그 라이브러리가 엘리먼트를 복제·이동시키면
내가 준 인라인 스타일이 새 문맥에서 전혀 다른 의미가 된다. "화면에서 숨기기"는 넘기는
엘리먼트 자신이 아니라 **바깥 래퍼**가 맡아야 한다.

### Phase 71 ✅ 지도 "고급 필터" 재검토 — 정기공고 날짜필터 버그 + 라벨 개선 (2026-07-29, v591)

**부수 수정**: 시급 슬라이더 하한이 10,000원으로 하드코딩돼 있었는데, 실제 최저임금

세 파일에 추가해 Android가 알고리즘 반전을 아예 안 하도록 함(이 프로젝트는 다크 테마를

동일 근거, `sw.js:72`).

### Phase 65 ✅ 랜딩 헤더 줄바꿈 수정 + 로고마크 + 언어 카드 2줄 정렬 (2026-07-28)

모바일 실기기 제보로 시작. **영어 화면에서 헤더의 "바로알바" 가 "로/알/바" 세 글자로 쪼개져
세 줄이 되어 있었다.** 한국어에서도 두 줄이었다.

**원인은 폰트가 아니라 헤더 폭 부족.** 헤더에 브랜드 + 언어 셀렉트(최대 132px) + 로그인 +
알바찾기 네 덩어리가 들어가는데, 390px 화면에서 넘치자 유일하게 줄바꿈 가능한 브랜드 텍스트가
글자 단위로 접혔다. 언어 버튼 문구가 한국어보다 훨씬 긴 언어들(러시아어 `Найти работу`,
네팔어 `काम खोज्नुहोस्`)에서 더 심했다.
