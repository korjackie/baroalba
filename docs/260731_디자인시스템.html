style.css + 바로알바.html + app.js 3파일 실측 (2026-07-31):

1순위 원인은 굵기다. 800·900이 848회로 전체의 절반 가까이 — 거의 모든 글자가 굵다. 전부 강조하면 강조가 사라지고, 위계 없이 시끄러운 화면이 된다.

2순위는 회색 8단계(#111 #222 #333 #555 #666 #888 #aaa #bbb, 약 1,350회)와 밝은 회색 5종(약 700회). 같은 역할에 매번 다른 값을 써서 화면 간 규칙이 안 맞는다.

디자인 토큰(--ink-900/600/400/200, --line, --r)은 2026-07-27에 이미 정의됐으나 절반만 적용된 상태다. 이 작업은 새 시스템을 만드는 게 아니라, 이미 정의된 시스템을 앱 전체에 관철시키는 것이다.

이 앱은 외국인·시니어 특화를 지향하므로(2026-07-29 확정), 전형적인 프리미엄 미니멀(얇은 글씨·넓은 여백)은 타겟 사용자의 가독성과 충돌한다. 굵기의 상대 위계만 정리하고 글자 크기와 정보 밀도는 건드리지 않는다.

Rollout
3. 적용 방식 — 축 단위 순차

화면 단위(홈→지도→상세…)가 아니라 축 단위로 앱 전체에 일괄 적용한다.

  • 화면 단위의 문제: 작업 중 "새 화면 반 / 옛 화면 반"이 되는데, 이 앱은 홈↔지도↔상세 전환이 잦아 그 불일치가 즉시 드러난다.
  • 축 단위의 이점: 매 단계가 전역이라 앱은 항상 일관된 상태를 유지한다. 각 축이 독립 커밋이라 롤백 단위가 명확하다.
차수축근거
1차글자 굵기체감 변화가 가장 크고, 색을 안 건드려 위험이 낮다
2차색 (회색·면·선)건수가 가장 많고 문맥 분기가 필요해 단독 배포
3차모서리 · 그림자시각적 마감. 1·2차가 안정된 뒤
4차간격 (4/8 그리드)레이아웃이 움직이므로 마지막. 별도 계획으로 분리
이번 구현 범위는 1~3차다.

--surface-1 신설 이유: 기존 --surface-2(#FBFCFD)는 거의 흰색이라 페이지 배경으로 쓰면 흰 카드가 배경과 분리되지 않는다. 페이지 배경용 단계가 별도로 필요하다.

🔴 문맥 분기 필수
실측: #f0f0f0은 border로 106회, background로 49회 사용된다. 같은 리터럴이 두 역할을 겸하므로 단순 문자열 치환은 금지한다. 치환 스크립트는 속성명을 함께 읽어 분기해야 한다. 
# 속성명으로 분기
border-color / border / border-*  : #f0f0f0 #eee #e5e7eb  →  --line
background / background-color     : #f0f0f0 #eee #e5e7eb  →  --surface-1

#eee·#e5e7eb도 같은 방식으로 문맥을 확인한 뒤 분기한다.

Process
5. 작업 절차 (매 차수 공통)
  1. 치환 스크립트 작성 — Node 스크립트, 문맥(속성명) 인식, 예외 목록 반영
  2. 드라이런 — 치환 건수와 예외 적중 건수를 먼저 출력. 판정 기준은 매핑표 실측 건수(예: 1차 900→700 284건). 10% 이상 어긋나면 중단하고 원인부터 찾는다
  3. 적용 → node --check 3파일(app.js sw.js shared-lang.js)
  4. 락스텝 5곳 동기화 — _APP_V / sw.js의 CACHE / 바로알바.html의 ?v= 4개
  5. 단독 커밋 — 축 1개 = 커밋 1개 (롤백 단위)
  6. 푸시 → 라이브 sw.js 버전 확인. 5분 넘게 안 바뀌면 vercel --prod --yes 수동 배포
  7. 실기기 확인 — 홈 / 지도 / 공고상세 / 마이페이지 / 업주 공고관리 5화면
Verify · Rollback · Scope
6~8. 검증 · 롤백 · 범위 밖
검증
  • 문법: node --check 3파일
  • 치환 정확도: 드라이런의 예외 적중 건수가 예외표와 일치하는지 대조
  • 잔여 리터럴: 각 차수 후 해당 축 리터럴이 예외 목록만 남았는지 재실측 (예: 1차 후 font-weight:800 잔여 = 0)
  • 시각: 실기기 5화면 스크린샷. 필요 시 Playwright 390px 실측
롤백

축 = 커밋이므로 git revert <sha> 한 번으로 해당 축만 되돌린다. 다른 축은 영향받지 않는다.

범위 밖 (YAGNI)
  • 기능 · 문구 · 레이아웃 변경 — 이번은 순수 시각 작업
  • 인라인 스타일의 CSS 클래스 이전 — app.js 전면 수술이라 위험 대비 실익이 낮다. 토큰 참조로 바꾸는 것만으로 목표(일관성)는 달성된다
  • 다크 모드 — 이 앱은 다크 테마를 설계한 적이 없고 color-scheme:light로 고정했다(Phase 66)
  • 브랜드 레드 · 로고 변경 — "브랜드 전체 재정의"는 선택하지 않았다
  • 모션 · 트랜지션 — 별도 축. 1~4차 완료 후 재평가
  • 글자 크기 27종 정리 — 절충안 선택에 따라 크기는 유지
Open Questions
9. 착수 전 확인할 것
  • font-weight: bold / bolder 등 숫자 아닌 표기의 존재 여부와 건수
  • #eee · #e5e7eb의 border/background 문맥 분포 (#f0f0f0은 106/49로 측정 완료)
  • 독립 HTML 포함 여부 — index.html · login.html · admin.html은 앱 CSS를 안 쓰므로 전역 처리가 자동으로 따라오지 않는다(Phase 68-B 교훈). 1차 착수 시 포함할지 결정 필요
