# 바로알바 작업현황 · 시스템구조 · 작업계획 — 2026-07-16(오후)~07-21

## 개요

지난 문서(260716_*, 07-16 05:26 작성) 이후 약 5일간 총 **32개 커밋**이 쌓인 구간.
겉으로는 스킬필터·바로브랜딩 배너·프로필편집 키보드가림 재수정 등 잔가지 작업으로
시작했지만, 이 구간 전체를 관통한 진짜 주제는 **"스키마 드리프트(schema drift) —
코드는 있는데 실제 DB에 없는 컬럼을 조회해 기능이 조용히 400으로 죽어있던 문제"의
전수 색출·근본 종결**이었다.

07-18~19에 `businesses.biz_type`·`businesses.plan`·알림 컬럼 등에서 조짐이 하나씩
드러났고, **07-21에는 클라이언트가 만지는 45개 테이블 + 서버함수(api/\*.js) + RPC를
살아있는 DB에 curl로 직접 대조해 16건의 "조용히 죽어있던 기능"을 일괄 색출·수정**했다.
그 과정에서 문서에 오래 남아있던 **P0("결제해도 새로고침/재로그인하면 plan이 free로
리셋")의 진짜 근본원인**이 `businesses.plan` 컬럼 부재였음을 밝혀내고 DDL로 종결했다.
SW는 v531→v548, Android는 versionCode 30·31 리빌드·배포.

이 구간의 가장 큰 산출물은 코드 수정 자체보다 **원칙 13-9 — "검수는 코드가 아니라
살아있는 DB에 대고 하라"**의 확립이다. "수차례 전면검수를 했는데도 이상없다고 했던"
버그들이 왜 반복해서 새어나갔는지에 대한 답이 여기에 있다: 코드 리뷰만으로는
스키마 드리프트를 잡을 수 없다.

### 발견된 근본 원인 패턴 (이 구간의 핵심)

이번 구간에서 반복해서 나타난 패턴은 **"스키마 드리프트 — 코드는 특정 컬럼을
조회하는데 실제 DB엔 그 컬럼이 없어(이름이 바뀌었거나, DDL이 실행 안 됐거나) 쿼리가
조용히 400으로 실패하는 것"**이었다. 특히 위험했던 건 **에러 삼킴 패턴**이다:

```js
const { data } = await db.from('businesses').select('region, ...');
// error를 구조분해하지 않아 400이 나도 data=null로 조용히 넘어감 → 화면이 빈 채로 정상인 척
```

- **`businesses.region`** — 4개 화면의 select에 들어있었으나 실제 DB에 없는 컬럼. 관련 화면들이 빈 결과로 조용히 죽어있었음.
- **`businesses.plan`** — 결제 후 이 컬럼에 PATCH하는데 컬럼이 없어 400. 문서에 오래 있던 P0("plan이 free로 리셋")의 진짜 근본원인. 구독은 `subscriptions`에 정상 저장되지만 클라이언트는 `businesses.plan`을 읽어 항상 free로 보였던 것.
- **`applications.created_at`/`reviewed_at`** — 실제로는 `applied_at`/`employer_reviewed_at`. 관리자 통계·리뷰 표시가 죽어있었음.
- **`businesses.owner_id` + 잘못된 조인키** — admin에서 모임 주최자 이름이 항상 공란이던 원인. `host_id`(=kakao_uid)를 workers는 `id`로, businesses는 없는 `owner_id`로 조인. 스키마는 멀쩡한데 **키가 틀린 의미 버그**라 컬럼 존재검사만으론 못 잡음.
- **`coupons.ticket_count`/`used_count`/`max_uses_per_user`** — 실제로는 `pass_qty`/`uses_count`/(부재). 쿠폰 지급수 undefined, 카운터 안 오름, **1인당 재사용 제한이 전혀 안 걸려 쿠폰 무한사용** 가능했음.

### 왜 "수차례 전면검수"에도 새어나갔나 — 원칙 13-9 확립

가장 중요한 산출물. "여러 번 전수검수 했는데 이상없다고 했던" 버그들이 반복해서
새어나간 이유는 **검수를 코드에 대고 했기 때문**이다. 코드 리뷰는 "이 컬럼이 실제
DB에 존재하는가"를 검증할 수 없다. 스키마 드리프트를 잡으려면 반드시 **살아있는
DB에 실제 쿼리를 날려(HTTP 200/400)** 컬럼 존재를 확인해야 한다.

```bash
# 컬럼 존재 검증 (200이면 존재, 400이면 없음)
curl -s -o /dev/null -w '%{http_code}' \
  "$SB/rest/v1/businesses?select=plan&limit=1" \
  -H "apikey: $ANON" -H "Authorization: Bearer $ANON"
```

이건 모델(소넷/오푸스)의 역량 문제가 아니라 **검증 방법론의 문제**다. 어떤 모델이든
코드만 읽으면 못 잡고, 살아있는 DB에 대조하면 잡는다. (13-8 "재해석 대신 복붙"에
이어 확립된 원칙.)

## 2. 시스템 구조 변경

### 2-1. 스키마 드리프트 전수 대조 — 45개 클라이언트 테이블 + 서버 + RPC

```
검증 방법: 코드의 모든 .from('테이블').select('컬럼') 및 api/*.js의 sb() 경로를
          스크립트로 추출 → 각 컬럼을 살아있는 Supabase REST에 curl로 개별 대조
          (HTTP 200=존재 / 400=부재)

발견·수정: 클라이언트 9건(v547) + 서버 admin.js·coupon.js 7건 = 코드 16건
한계:     URL 쿼리 컬럼은 스크립트로 전수 대조되지만, INSERT/PATCH 바디의 키와
          obj.컬럼 속성 접근은 코드를 눈으로 읽어야 잡힘(coupon.js가 그 사례).
```

### 2-2. P0 근본 종결 — businesses.plan 영속화

```
증상(오래된 P0): 결제해도 새로고침/재로그인하면 플랜이 free로 리셋
진짜 원인:       toss-confirm.js가 결제 후 없는 businesses.plan을 PATCH(400).
                구독은 subscriptions에 정상 저장되나 클라이언트는 businesses.plan을
                읽어서 항상 free로 보였음.
해결:            ALTER TABLE businesses ADD COLUMN plan + subscriptions에서 백필.
                로그인 시 select('*')로 이미 plan을 읽고 있어(app.js:11808/11830)
                컬럼만 생기면 즉시 정상 동작 → end-to-end 검증 완료.
```
